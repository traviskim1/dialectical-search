10/28/26 App Overhaul
I want to do a large overhaul of my current setup for dialectical search because I think that a lot of the backend is messy and unclear. I will use basketball as a running example, but remember that other activities should be considered.

The flow should be as follows:
User explains an activity they are interested in and their current state in that activity. The search bar should say: “Tell me about an activity you are interested in. Describe the ways you have engaged with it in the past, things you feel you are not doing enough and things you feel you already understand well.” 
From the user response to this initial search, the LLM should extract the activity described using a query prompt and store it as variable ACTIVITY. The LLM should also extract user-specific context about the activity and update the activity’s value tree (see following sections for what these mean). Finally, if the LLM realizes it needs more context, it should ask specific questions to the user (e.g. how long have you been doing this activity, how often), and these questions should also be specific to the activity when necessary.
The LLM should build a tree map of the activity. The tree’s root node should be the activity. The first set of children should be the broadest dialectical values from that activity. The broadest dialectical values should be ones that cannot be simply taught, like teamwork or bodily awareness. For example, in basketball, these are values inherent to the sport and must be learned by engaging in basketball directly. The value of teamwork encompasses all of team-based basketball games, ranging from skills like making good passes to strong communication. This is not something that can be learned simply by being told to focus on “teamwork” because the user has no idea where to begin or whateven constitutes teamwork. However someone more experienced can understand this value as the culmination of their experiences and time put into basketball. The same goes for all activities. There are many broad and dialectical values which cover so many parts of the activity that it is impossible for that dialectical value to be understood simply through communication. Or, another example: bodily awareness is something that needs to be learned through engagement and the strengthening of muscle memory, not something that can be taught via text and then suddenly realized. After the broadest dialectical values should be action-specific or context-specific principles. What I mean by this are aspects relating to the broader dialectical value but specific to the activity itself. For basketball, if the dialectica value is teamwork, then context-specific principles can be things like off-ball movement and passing. These are, similarly to dialectical values, values of the game that cannot be quickly understood by someone unfamiliar with these values, but they are also less abstract and tied to the activity itself. For example, passing is pretty clearly something beneficial for basketball, but if a new player is told to focus on passing because it will help build teamwork, they won’t understand how to focus on passing or what the value of passing or teamwork even are because they don’t have the right support to engage properly in these values. This brings us to the final set of children, this time a set of actions derived from the context-specific principles. These actions are concrete and are often named. In sports for example, these examples can be types of plays or specific movements. These actions can be explained simply and clearly and have concrete reasons for why they are performed within the limited context of a new participant. New participants have a limited range of understanding an activity—because they are new. That also means they have a limited range of understanding why certain actions are beneficial to an activity. Concrete actions are a good place to start because they can operate within this limited range of understanding while simultaneously serving to expand the user’s activity framework. The goal is that by specifying a concrete set of actions for the user to incorporate in future engagement with the activity, we can then drive the understanding of broader context-specific principles which then drive some understanding of dialectic values within the activity. Finally, by building the user’s value of the activity by allowing them to understand why each action is important and how each action fits into the context of action-specific principles and dialectic values, we can hope to “jump start” the user’s engagement with the activity in a dialectical way so they don’t get stuck in the following failure modes.

Failure modes of engagement levels:
User is stuck on context-specific principles and has no idea how to actually incorporate these values. For example in basketball, a new player who is focused on the value of passing does not know how actually to incorporate that engagement. For instance, they might know to pass to open teammates, but they might not know the patterns of teammate movement necessary to incorporate an engaging and successful play. The give and go pass for example requires a contextual understanding of concrete plays, where the player passes the ball to another player and then immediately sprints towards the basket to get the ball passed back to them. Someone new to passing doesn’t understand that after they pass the ball and there’s an opening to the basket, they should run straight to the basket to try to induce a give and go. Or, even if they do understand this, they might not understand when not to induce a give and go pass (e.g. if there is a very tall person directly in their path)
This same failure mode applies to a fixation on dialectic values.
User is stuck within a specific set of actions or context-specific principles and does not know how else to engage with activity. For example in basketball, a new player might only be focused on making 3-point shots into the basket because that is how they have seen Stephen Curry succeed in the sport when watching. That new player might then put many hours into practicing their shooting form so they can attempt these shots in game, but then they neglect ways of engaging in the sport outside of shooting (e.g. off-ball movement, passing, defending, getting rebounds, etc.). This then limits their engagement in the activity and might make them get frustrated when the only way of engaging in the activity fails (e.g. they can’t make shots). A benefit of engaging with an activity in many ways is then that the user has many ways of finding joy in the game. Even if someone doesn’t make any shots in a game, if they are consistently finding great passes and assists and make a lot of good steals, they can not only have a high impact on the game, but also have a lot of fun.

Returning to this tree of dialectic values, context-specific principles, and action sets: we need to gather context on the user so that we can update the tree. Each node on the fringe contains a specific action. There can be duplicate actions on the fringe. For example, dialectic values of basketball could be teamwork and bodily awareness. These could extend to reach the same action node: teamwork -> off-ball movement -> setting screens OR: bodily awareness -> using your body and positioning -> setting screens. As you can see there are moments where actions can overlap between values. This is completely fine and actually valuable to the architecture I am suggesting. User context must be extracted from their prompt and can be categorized most simply in three ways. The first way is relevant user knowledge. For example, if the user is focused primarily on shooting the basketball and making sure the opponent gets less shots into the basket (which is the simplest and most straightforward way of understanding the game of basketball), then that means their relevant knowledge is focused on shooting and defending and there is a massive gap in relevant skils like off-ball movement, e.g. setting screens, boxing out, making cuts, etc. This provides valuable context for what the user should focus on instead, if there is a massive gap in their knowledge. Off-ball movement is incredibly important to making the opportunities to play effective offense and defense, and it’s fair to say that one cannot effectively engage in offense or defense without having strong off-ball movement. Therefore this gap in relevant user knowledge should guide this app to suggest off-ball movement related actions because this is a critical gap in user knowledge. The way this app should do this is by building a profile on the user and using this profile to update the tree of value nodes. If the user understands that making a lot of shots into the basket is valuable to the sport, then we can check off from the tree concrete actions like “taking shots when open” or “not being afraid to shoot the ball” because clearly the user already understands these ways of engaging in the activity. 
The second major user context is the user’s experience level. Many actions might be literally impossible to the user based on their experience level (e.g. dunking) or might be too unrealistic to explain or access to the user. For example a give and go pass is a nuanced play requiring an understanding of not only how to induce plays by making movements and understanding teammate skill levels, but also requiring a simultaneous awareness of defender capabilities and positions. For a new player, this is not a great solution because it is pretty difficult to understand. For a more experienced player who is already pretty good at making basic passes, this can be a very valuable suggestion because it opens up the player to engaging in the activity in new ways. The experience level of a user is very important to consider because it can guide the specific actions we recommend to the user. The way user experience should be stored is: in each fringe node, there should be a two weights, one called principle-specific experience level needed and experience level needed which are two simple 1-10 point scale where 1 means any beginner can figure this out and 10 means that this is something very difficult. Principle-specific experience level means that if the user is very knowledgeable about the specific actions relative to the principle, then they should have a better time understanding a more difficult action, even if their overall experience is lower. Principle-specific experience level and overall experience level can vary by action. For example, a specific pass might need a high principle-specific experience level because it incorporates the parts of many actions within that principle, but need a low overall experience level because making the pass itself isn’t that hard. Conversely, something like a dunk needs a high overall experience level, but one does not need to know the first thing about shooting to be a good dunker (e.g. Shaquille O’Neal). When this app suggests specific actions, the model should weight both types of experience levels needed for that specific action and the user’s understanding of relevant activity-specific knowledge (e.g. even if the user’s experience is more like a 3, if they know a LOT about passing, then suggesting a 5/10 difficulty pass might be viable). 
The final user context are miscellaneous user-specific details unrelated directly to activity-relevant knowledge or experience level. For example, I, as a user engaging in basketball, am a heavier male. This means that I have the advantage of being able to use my weight to get myself closer to the basket and push people back. This makes me more effective at making layups, playing in the paint, and playing for step-back shots by leveraging my weight. This context that I am a heavier person is something needed to suggest specific action sets, but it is unclear where exactly this information should be stored.
The main decision of action-set suggestion should be by suggesting activities within activity-specific principles that are significantly underweighted by the user’s activity-relevant knowledge (e.g. if the user is focused on shooting and defending, they have a big gap in off-ball movement). This should also be supported by a separate query which asks an LLM “What do people with similar [activity-relevant knowledge and experience level to the user] usually miss” e.g. “What do beginners in basketball usually miss”: and the answer is often off-ball movement. Then, the model should take the outputs of specific suggested actions and locate them on the tree. The model should then consider the experience level needed to incorporate that specific action, what other actions related to that context-specific principle are already incorporated within the user’s activity-relevant knowledge base/engagement in the activity, and any miscellaneous user-specific context.
The app should suggest, as it already does, 2-3 user specific actions. The app should, as it already does, ask for feedback after the user engages in the activity. The feedback should be in two parts. The first part should ask for free-response feedback asking the user to describe what stood out to them when engaging in the activity in that specific way and things they noticed. The second part should ask guided questions which ask about specific things the user might notice about the action and relevant contextual information relating to the action to try to guide the user to think about the context-specific principles of the action. Both of these feedbacks should be used to update the user context in any of the 2-3 ways: relevant knowledge, experience level, or miscellaneous. The value-tree should also be updated, including when unrelated facts about user-relevant knowledge are included. For example, when incorporating a step-back shot into gameplay, the user notes that they also realized that they can pay attention to their defender’s legs for when they attempt a shot. They notice that if their defender’s legs are farther apart, that makes it harder for the defender to jump up and try to block their shot. This is a new aspect of activity-relevant knowledge that should also be incorporated into the value-tree and to cross off that specific action, even though it was unrelated to the suggestion of a step-back shot. Also, if the user mentions that they successfully incorporated the step-back shot into their game play, then that should be crossed off of the action set too. 

When suggested an action, the user might not fully understand that action. If the user gives feedback and explains that they weren’t able to incorporate that action, the model can support the user depending on the failure mode of the understanding. Some failure modes are as follows:
User tries a new action but is scared to fully incorporate it in their activity. Addressing fear is difficult and may require backtracking to suggest fear-breaking actions. For example if bravery/openness to new action is a context-specific principle, then if the user is scared of trying X, then we might want to step back and suggest fear-breaking actions first, and then move back to X. Another option is to explain why the model is suggesting that specific action. For example, if I say I am scared of the step-back shot because I am afraid of making physical contact with the defender, the model might reassure me by first affirming my fear and then explaining that as a larger person, making physical contact should be part of the game and that I should be using my size to make more plays and support the team. 
Model suggests user action X but user misinterprets and still focuses on action Y: For example, in basketball, the model might suggest me to focus on making right-side layups (because I am right handed and because I am heavy and can play towards the basket), but I might instead focus on shooting because I conflate the two to be one and the same. Already in suggesting layups is an implicit challenge to the user’s conception of the game. The model is suggesting the user focuses less on making shots and more on layups. This requiers a reiteration of what the model wants, asking specific questions about how the user notices that layups work effectively for their skillset for example, or explaining why the model is suggesting layups and why they will be more effective than focusing on shooting. 
The model should address these failure modes in the following ways, by challenging misinterpretations and affirming and supporting fears. The model should ask the user to try again if they fail to properly engage in the specific action set and continuously update the user profile.

From a high-level overview, the flow of the app should be as follows:
User describes activity
Model asks follow up questions if necessary
Model creates value-tree of activity and also a running user profile stored both in the value-tree (e.g. user’s activity-relevant knowledge) and outside of the value tree (user’s experience level and miscellaneous information).
Model finds the context-specific principles that are most underweighted given the running user profile proportional to the amount of action nodes for that context-specific principle. The less information the model has, the more the model should consider the query of “what do people most like the user miss the most of in this activity”; i.e. in the beginning the model should heavily consider the question “what do beginners think the least about in activity X” to guide its understanding of what is underweighted.
Model suggests 2-3 actions from the context-specific principles most aligned to the user’s experience level. Actions should be clearly defined, specific, and explained.
Model asks user for feedback on how their experience was focusing on these specific actions. First the model asks for general feedback, then the model asks for specific feedback, asking guiding questions that lead the user to think about the context-specific principles (but in a way that isn’t overtly leading). 
If the user has engaged with the action set properly, the model updates the user context given feedback. If the user fails to engage with the action set, the model either challenges misinterpretation or affirms and explains reasoning if the user is scared to engage and then asks the user to engage again. If the user continues to fail to engage, after the third attempt, the model will backtrack and remap user context to focus on building up relevant deficiencies. For example if the user is scared then the model will realize that focusing on getting over fears in the activity is a context-specific principle that is more underweighted than others.
The model should also ask the user for feedback in general unrelated to any specific actions on ways they found they engaged more in the activity. This feedback should also be used to update the user context
Steps 2-8 should be re-run, this time suggesting new specific actions that are decided upon by the user-context and what other people similar to the user miss out on, but this time the second query is downweighted since there is more user context.
The hope is that on continuous iterations of steps 2-8, the user can find more and more ways of engaging in the activity and hopefully build up their understanding of context-specific principles and dialectical values by engaging in many sets of actions. 


I will provide a concrete example using myself as someone trying to learn basketball:
I want to get better at basketball so I tell the model: “I am getting into basketball and I play around 4 hours a week with my friends casually. Right now I am focused on getting better at shooting and defending because I feel like I am not a good teammate right now because I can’t make any shots into the basket or defend that well. Because of this, my teammates aren’t passing to me as much and that makes the game less fun.”
The model asks me: “how long have you been playing lately?” and I answer: “Around one month”
The model creates the value tree. The model creates my user profile as: relevant knowledge focuses on shooting and defending, and because the model knows I am trying to take shots, it crosses off specific actions like taking shots, and downweights actions like taking low range shots, mid range shots, and long range shots (but not crossing them off because it is unclear which ones I am engaging in). The model also recognizes that I am aware about defense. The model also categorizes my experience level as new because I’ve only play four hours a week for the past month.
The model finds that I am least focusing on the context-specific principle of off-ball movement because I only talk about defending and shooting, so no children/action nodes are crossed off releative to off-ball movement. The model also knows that when asking “what do new players usually miss out on,” one of the answers will be off-ball movement.
The model suggests that I focus on setting screens and boxing out. The model explains how I should set a screen and why it works and does the same for boxing out. I go out into games and apply these actions. 
The model asks me for feedback and I give the following general feedback: “When I was setting screens, I realized that I can have a big impact on the game even when I’m not directly on the ball. I also learned that I can use my bodily positioning to help my teammates, and this works well because I am a larger guy.” I also say: “I remembered advice that my friend gave me to only take shots when my teammates are available to get the rebound. Boxing people out made me understand what that availability looks like, and also reinforced my understanding of my bodily positioning”. The model asks me “Where were the defenders when you set the screen?” and I respond “There was one defender against my teammate who had the ball at the top of the key. I was to the defender’s left. By standing in my defender’s way, my teammate could run around the both of us, and I could hold off two defenders, because my defender was also on me.” The model asks me: “Where was your opponent standing when you were boxing them out?” and I answer “They were also trying to box me out or run around me to where the ball might bounce to after hitting the rim or backboard. I noticed their movement.” 
I have engaged with the action set properly and the model update scontext in a few ways. The first way is that the model updates the action set in the value tree to reflect that I have engaged in setting screens and boxing people out and now incorporate that in the game, so these won’t be suggested again for a while. These can also be crossed off across multiple principles (e.g. across principles of off-ball movement, teamwork, and bodily awareness). The model also updates its miscellaneous user knowledge to the fact that I am a heavier/larger man, which means that I can be better suited for actions that are advantageous to a heavier/larger man. The model also updates its context on my relevant knowledge based on my explanation of a prior experience where my friend told me to only take shots when my teammates are available for rebound. This is also a specific action that could be suggested, so now the model knows not to suggest it because I already think about it. Finally, the model can update my experience level both in the game and in off-ball movement because my specific feedback reflected a broader understanding of how to engage with the game based on off-ball movement.
The model asks me what else I learned in general and I respond by saying I learned how to shoot while jumping because my friend taught me, which is also a new relevant knowledge that should be updated. 
Steps 2-8 are rerun, this time suggesting new specific actions. This time, the model decides that I am not thinking about layups or step-back shots, two types of shots that are specific to my user context. For example, I am a heavier guy which means that I can be more effective closer to the rim, and I can use my size to push people back for a step-back shot. The model can incorporate this into its feedback. Shortly: I give feedback saying that I didn’t layup because I was focused on shooting. The model realizes this as a failure mode of engagement because of misinterpretation and challenges my focus on shooting while explaining why: I should be playing for layups because of my size. It asks me to try again, and I do, and I explain that I made a few layups in a game and it was much easier to make these shots as a newer player. For the step-back shot, I give feedback that I’m afraid of making contact. The model recognizes this as a failure mode and gives similar feedback to when I misinterpreted layups. The model suggests the benefit of playing for a step-back shot because of my weight while also explaining that my learning to shoot while jumping from earlier can support this. From a meta-view, the model likely suggested the step-back shot because it understands that I learned to shoot while jumping, and that is something that requires more principle-specific skill (e.g. shooting-specific skills) and allows me to actually engage in the step-back shot. The guided feedback here might be to notice the defender’s legs, and I might give this feedback: “I noticed that when my defender’s legs are wide, I have room to shoot”, and the model updates my profile to also reflect that I am also looking at my defender’s body to find opportunities to make shots. 
Hopefully the model continues to iterate and provide new suggestions, after all feedback requirements and action engagements are met. 


Changes since this spec (added by Claude on 11/11/26 and 11/12/26; everything above is Travis's original text, unchanged)
These are the places where the app now differs from, or adds to, the text above. Details are in CLAUDE.md.
Less obvious suggestions. The tree is selective (2-4 actions per principle instead of every way of acting) and leaves out the basics. The person is assumed to know a bit more than their stated level (one point on the 1-10 scale) when deciding what is within reach.
Impact. Each action has a third 1-10 rating, impact: how much doing it changes how the activity goes for the person and whoever they do it with. Within reach, higher-impact actions are suggested first (in basketball, a screen before a J-cut), and a high-impact action can be chosen over a lower-impact one from a slightly more neglected principle.
Names. When an action is a standard, named part of the activity, the model uses that name (a screen, not "block a defender with a still, angled body") and the card explains it once.
Step 3, timing. When there are follow-up questions (step 2), the tree starts being built while the person answers them, because the tree depends only on the activity and not on the answers. The tree and everything after it are the same; the person just waits less. Nothing else in the order of steps 2-8 changed.
The "what do people like this usually miss" query (11/12/26, for speed). It is still a separate query, asked without the tree in view, and its answers are then located on the tree, as described above. What changed is when it runs: at the same time as the profile update, so it uses the person's knowledge and experience level as they were just before that update. The weight on it is unchanged (heavy at first, lighter each round).
Writing the suggestions (11/12/26, for speed). The 2-3 actions are still chosen together, but each one's explanation is written separately and at the same time. So that the explanations don't describe the same situation, the model gives each chosen action its own moment when it chooses them, and an action the person is asked to try again keeps the moment it had before.
Running online. The app runs online for many people at once. Participants use Claude Sonnet 5.5 through the API by default (Ollama only when the researcher picks it). Each participant sees only their own journal, through a private link; there is no list of journals for them. Every journal, with every prompt and reply, is saved in a database, and the researcher view (password) can open any journal and download them all.
